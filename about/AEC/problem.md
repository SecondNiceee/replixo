# AEC — Проблема (зачем мы всё это делаем)

## Симптом

Когда один участник демонстрирует **«весь экран со звуком»** (например, ролик
на YouTube, игру или музыку), остальные участники слышат **эхо собственного
голоса**. То есть демонстрирующий транслирует не только контент экрана, но и
голоса других людей, которые в этот момент играют из его же динамиков.

## Почему это происходит

При захвате системного звука через OS loopback («поделиться экраном со звуком»)
операционная система отдаёт нам **всё, что сейчас играет на выходе** этой
машины. А на выходе играет не только контент (YouTube/игра), но и **голоса
остальных участников звонка**, которые микшируются туда WebRTC-воспроизведением.

```
Динамики машины A играют:  [ контент экрана ] + [ голоса участников B, C, D ]
OS loopback захватывает:   ВСЁ это целиком
A публикует в звонок:       контент + голоса B, C, D
Участник B слышит:          свой собственный голос обратно  → ЭХО
```

Чем больше задержка вывода (Bluetooth-наушники, буферы ОС), тем более
«поздним» и заметным становится это эхо.

## Почему обычный AEC тут не подходит

Классический AEC для микрофона/динамика (как в спикерфоне) рассчитан на то, что
**ближний конец (near-end) — это твой голос, и он звучит с перерывами**. Поэтому
такие алгоритмы «замораживают» адаптацию во время double-talk (когда говорят
одновременно оба конца).

В нашем случае ближний конец — это **контент экрана**, который играет
**практически непрерывно** (фильм, игра, музыка). Если замораживать адаптацию
каждый раз, когда есть контент, фильтр **никогда не сойдётся**.

Именно поэтому нельзя взять готовый спикерфонный AEC — нужна другая стратегия
(см. `solution.md`).

## Почему `restrictOwnAudio` / loopback-хаки не спасают

- Браузерный флаг ограничения собственного звука работает только для режима
  «вкладка Chrome», а не для «весь экран». На Windows при захвате всего экрана
  ОС всё равно отдаёт реальный микс с выхода динамиков.
- Простой loopback-трюк (вычесть заранее известный сигнал «как есть») не
  работает, потому что путь эха неизвестен: у него своя **задержка**,
  **громкость** и **частотная окраска**, которые ещё и плывут во времени
  (дрейф тактовой частоты звуковой карты, изменение громкости ОС). Нужен
  **адаптивный** фильтр, который сам подстраивается под этот путь.

## Что считаем успехом

- Участники **не слышат свой голос** обратно во время демонстрации экрана.
- Контент экрана (YouTube/игра/музыка) проходит **без искажений** — без
  «музыкального шума», без «плавающего»/«качающегося» звука, без провалов.
- Решение **не делает хуже**: если фильтр не сошёлся или что-то пошло не так,
  публикуется сырой звук без регрессии.

Метрика качества — **ERLE** (Echo Return Loss Enhancement, в дБ): насколько
тише стало эхо на выходе относительно входа. Положительный и растущий ERLE =
эхо давится; отрицательный ERLE = фильтр разошёлся и сам добавляет эхо.
