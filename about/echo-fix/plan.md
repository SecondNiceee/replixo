# План детерминированного фикса эха для десктопа (Electron / Windows)

> Цель: убрать эхо при демонстрации экрана **на уровне ОС**, как это делают Zoom,
> Discord и OBS — без опоры на DSP-подавление (AEC-воркл��т остаётся только как
> запасной слой). Приложение НЕ переписывается: добавляется нативный аудио-компонент
> рядом с существующим Electron + Next.js.

---

## 0. TL;DR

- **Проблема:** в Electron `getDisplayMedia({ audio: "loopback" })` захватывает
  **весь системный микс**, куда наш renderer уже подмешал голоса участников звонка.
  Constraint `restrictOwnAudio` до системного loopback **не доходит** (это фича
  tab-capture Chromium, не системного захвата). Поэтому голоса возвращаются в
  звонок → участники слышат себя.
- **Правильное решение на Windows 10 (2004+) / 11:** WASAPI **Process Loopback**
  в режиме `EXCLUDE_TARGET_PROCESS_TREE` с PID нашего Electron. Это «настоящий
  restrictOwnAudio» на уровне ОС: захват = весь звук системы − звук нашего процесса.
- **Драйвер (виртуальный аудиокабель) нужен ТОЛЬКО как fallback** для Windows
  старше 2004. Он требует EV-сертификата и attestation-подписи Microsoft.
- **Итог:** для актуальных Windows драйвер не обязателен. Но раз задача — «чтобы
  при скачивании вставал драйвер», ниже описаны ОБА пути: (A) предпочтительный
  driver-free и (B) полноценная установка драйвера через NSIS.

---

## 1. Почему JS-предел уже достигнут

| Что нужно | Доступно в Chromium/JS? |
|---|---|
| «Весь системный звук» | Да — `audio: "loopback"` |
| Заглушить локальное воспроизведение захваченного | Да — `"loopbackWithMute"` |
| Исключить звук СВОЕГО процесса из захвата | **Нет** — только нативный WASAPI |
| Захват звука КОНКРЕТНОГО приложения | **Нет** — только нативный WASAPI |

Вывод: дальше — только нативный код (C++/Rust) рядом с Electron. UI и логика
звонка не трогаются.

## 2. Архитектура решения

```
┌─────────────────────────── Electron (renderer, Next.js) ───────────────────────┐
│  Звонок (mediasoup) + воспроизведение голосов через AudioContext.destination    │
│                                                                                 │
│  getDisplayMedia:                                                               │
│    video  → как сейчас (выбранный source из кастомного picker'а)                │
│    audio  → БОЛЬШЕ НЕ "loopback". Вместо этого — PCM-поток от нативного модуля   │
└───────────────▲─────────────────────────────────────────────────────────────┬─┘
                │ PID Electron (exclude)                     PCM (float32/48k)  │
                │                                                               ▼
        ┌───────┴───────────────────────────────────────────────────────────────┐
        │  Нативный аудио-компонент (Node N-API аддон ИЛИ helper .exe)            │
        │  WASAPI Process Loopback, режим EXCLUDE_TARGET_PROCESS_TREE(pid)        │
        │  = весь системный звук − звук дерева процессов Electron                 │
        └────────────────────────────────────────────────────────────────────────┘
```

Ключ: голоса участников проигрывает **наш** renderer (дерево процессов Electron),
поэтому `EXCLUDE_TARGET_PROCESS_TREE` их вырезает физически, до попадания в захват.

## 3. Вариант A (РЕКОМЕНДУЕТСЯ): Process Loopback, без драйвера

### 3.1. Требования
- Windows 10 версии **2004 (build 19041)** или новее, либо Windows 11.
- Electron остаётся текущей версии (Chromium 148 — ок).

### 3.2. Нативный модуль
Реализовать процесс-лупбэк через WASAPI:
- `ActivateAudioInterfaceAsync` с `VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK`.
- `AUDIOCLIENT_ACTIVATION_PARAMS`:
  - `ActivationType = AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`
  - `ProcessLoopbackParams.TargetProcessId = <PID Electron main или renderer-дерева>`
  - `ProcessLoopbackParams.ProcessLoopbackMode = PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`
- Формат: 48 kHz, float32 (совпадает с Web Audio), заполнять тишиной при отсутствии данных.
- Выдавать PCM-кадры наружу (в renderer).

Две формы поставки (выбрать одну):

**A1. Node N-API аддон (`.node`)**
- Язык: C++ (или Rust через `napi-rs`).
- Сборка: `node-gyp` / `prebuild` для x64.
- Плюс: живёт внутри процесса, простая передача буферов.
- Минус: нужно пересобирать под версию Node/Electron (`electron-rebuild`).

**A2. Отдельный helper `.exe` (предпочтительно для стабильности)**
- Язык: C++ или Rust.
- Стримит PCM в Electron через stdout-pipe или локальный сокет.
- Плюс: не зависит от ABI Electron, обновляется независимо, проще подписать.
- Минус: нужно управлять жизненным циклом дочернего процесса.

### 3.3. Интеграция в поток захвата
Файлы, которые затрагиваем (добавление, не переписывание):

- `electron/main.js`
  - В `setDisplayMediaRequestHandler`: **перестать** возвращать `audio: "loopback"`
    для случая, когда доступен process-loopback. Видео — как есть.
  - Запустить нативный захват, передать ему PID (`app`/`webContents` дерева).
  - Прокинуть PCM в renderer (IPC / `MessageChannelMain` для потока).
- `components/electron-patches.tsx`
  - После получения video-only `MediaStream` из `getDisplayMedia`, создать
    аудио-трек из PCM нативного модуля (через `AudioContext` +
    `MediaStreamAudioDestinationNode` или `AudioWorklet`), добавить трек в стрим.
- `hooks/mediasoup/use-media-controls.ts`
  - Ветка Electron: вместо `getScreenAudioConstraint()` (loopback) использовать
    аудио-трек от нативного модуля. Веб-ветка не меняется.
- `preload.js`
  - Экспонировать API старта/стопа нативного захвата и канал PCM.

### 3.4. Проверка
- Демонстрация всего экрана со звуком (плеер/YouTube) → зрители слышат медиа,
  но **не слышат собственные голоса**.
- Тест «десктоп демонстрирует → браузер смотрит»: у смотрящего нет своего эха.
- Убедиться, что при `TargetProcessId` = дерево Electron исключается именно наш звук.

## 4. Вариант B: Виртуальный аудиодрайвер, ставится при установке

> Нужен только для Windows < 2004 или как «Zoom-подобный» универсальный путь.
> Это то, о чём вопрос «чтобы при скачивании вставал драйвер».

### 4.1. Что за драйвер
Виртуальное аудиоустройство (WDM/APO), как VB-CABLE: ОС видит его как звуковую
карту, выход соединён со входом внутри системы. Схема разводки:

- Голоса участников звонка → реальные наушники (их захват не видит).
- Демонстрируемый звук приложения → виртуальное устройство.
- Захват демонстрации → только вход виртуального устройства.

### 4.2. Юридический/технический барьер (ВАЖНО)
- Kernel-mode драйвер на Windows требует:
  - **EV Code Signing Certificate** (Extended Validation, аппаратный токен).
  - **Attestation signing** через Microsoft Partner Center (Hardware Dev Center).
  - Регистрацию в программе Windows Hardware.
- Это платно, требует юрлица и занимает время на модерацию.
- Готовые драйверы (VB-CABLE и т.п.) имеют лицензионные ограничения на
  распространение внутри своего инсталлятора — нужна коммерческая лицензия.

### 4.3. Установка драйвера через NSIS (у нас `oneClick: false`)
Текущий `electron-builder.yml` уже даёт кастомный NSIS-инсталлятор. Шаги:

1. Собрать/лицензировать подписанный драйверный пакет (`.inf` + `.sys` + `.cat`).
2. Положить его в ресурсы сборки (`build/driver/`), добавить в `extraResources`.
3. Кастомный NSIS-скрипт (`installer.nsh`, макрос `customInstall`):
   - Запустить тихую установку драйвера: `pnputil /add-driver driver.inf /install`
     (нужны права администратора — NSIS с `requestedExecutionLevel: admin`).
   - Создать/настроить виртуальное устройство, задать имя для распознавания в app.
4. При удалении (`customUnInstall`): `pnputil /delete-driver ... /uninstall`.
5. В приложении: находить это устройство по имени и захватывать только его.

### 4.4. Минусы варианта B
- Дорого и долго (сертификаты, подпись, поддержка).
- Драйвер уровня ядра = риск синих экранов, конфликты с антивирусами.
- Требует прав администратора при установке.
- Поэтому — только если Вариант A недоступен.

## 5. macOS (на будущее, сейчас собираем только --win)

- Нет прямого аналога process-loopback в JS.
- Пути: **Core Audio taps** (macOS 14.4+ `AudioHardwareCreateProcessTap`,
  умеет исключать процесс) или аудиорасширение/виртуальное устройство
  (как BlackHole). Требует нотаризации Apple.
- Отложить до появления потребности в macOS-сборке.

## 6. Слои защиты (итоговая стратегия)

1. **Основной (детерминированный):** WASAPI Process Loopback, exclude своего PID
   (Вариант A). Убирает эхо физически.
2. **Fallback для старых ОС:** виртуальный драйвер через NSIS (Вариант B).
3. **Последний слой:** существующий AEC-воркл��т (`about/AEC/`) — **сейчас
   ОТКЛЮЧЁН** (`AEC_ENABLED = false` в `hooks/mediasoup/use-media-controls.ts`).
   Код сохранён; включать только если оба верхних слоя недоступны (например,
   старый Windows без драйвера), вернув флаг в `true`.

## 8. Ответы на исходные вопросы

- **«Почему нельзя сделать это в самом приложении (JS)?»** — потому что исключение
  своего процесса/захват конкретного приложения не выражается через
  `getDisplayMedia`. Это нативный API ОС. Решение — добавить нативный модуль,
  переписывать приложение не нужно.
- **«Можно ли ставить при установке?»** — да, `oneClick: false` NSIS позволяет
  кастомные шаги установки (Вариант B). Но с Process Loopback (Вариант A)
  отдельная установка драйвера вообще не требуется — нативный модуль едет внутри `.exe`.
- **«Discord/Zoom ставят аудиокабель?»** — да, они встраивают собственный
  аудиокомпонент уровня ОС (драйвер/хук/расширение) в инсталлятор. Современный
  аналог без драйвера — именно WASAPI Process Loopback (Вариант A), который сейчас
  используют OBS и новые версии Discord.
